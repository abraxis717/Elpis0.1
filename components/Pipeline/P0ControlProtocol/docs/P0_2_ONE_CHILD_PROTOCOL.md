# P0.2 One-Child Affine Expansion Shadow Protocol

## Four-Stage Expansion Vocabulary

| Stage | Description | Authority |
|-------|-------------|-----------|
| EXPANSION_PROPOSAL | Model proposes one or more structural expansion cells. | Proposal-only. No authority consumed. |
| EXPANSION_ADMISSION | Controller validates semantic identity, policy, ranking, budget feasibility. Selects at most one cell. | Evidence only. No resource authority consumed. |
| CHILD_ALLOCATION | Admitted RequestAccount allocates one child, consumes parent predecessor capability. | Sole parent-side affine authority transition. |
| CHILD_EXECUTION | Child account consumes its own refinement charge, frozen TRM emits proposal. | Pure computation. Controller-owned accounting already committed. |

## Authority Classification

| Operation | Authority Type | Consumes Resource? |
|-----------|---------------|-------------------|
| Parent TRM proposal | Model computation | No |
| Expansion proposal evidence | Evidence record | No |
| Admission decision | Controller validation | No |
| allocate_child | Controller affine transition | Yes: predecessor capability, spawn cost, child allocation |
| charge_child_refinement | Controller affine transition | Yes: child root capability, refinement charge |
| seal_child | Controller state transition | No |
| close_child (COMPLETED) | Controller affine transition | Yes: parent lease, registered refund |
| close_child (ABORTED) | Compensating child closure | Yes: parent lease, registered refund |
| Fold | Deterministic structural operation | No |

## Child Seed Rule: `child_seed.copy_void_cell.v1`

1. Copy complete parent `proposed_grid81`.
2. Set the selected expansion cell to VOID token (0).
3. Preserve every other cell.
4. Preserve structural semantic-space identity.

Child request ID is derived deterministically from:
- Parent request ID
- Parent structural digest
- Chosen cell
- Fixed domain separator

Internal L0 account IDs and capability IDs are generated by the authority implementation.

## Fold Rule: `fold.replace_cell.v1`

On successful child proposal:
- If `child_proposed_grid81[chosen_cell] != EXPANSION`: `folded_token = child_proposed_grid81[chosen_cell]`, `unresolved_expansion = false`
- Else: `folded_token = VOID`, `unresolved_expansion = true`

On child abort:
- `folded_token = VOID`, `unresolved_expansion = true`

Only the chosen parent cell may change during this fold.

The fold must NOT:
- Merge residual vectors
- Authorize another child
- Execute an expert
- Emit an artifact
- Authorize STOP

## Conservation Equations

### Parent while child is open (per granted axis):
```
B0_parent = R_parent + S_parent + A_child
```
where `A_child` is the original registered allocation.

### Child (no grandchildren in P0.2):
```
A_child = R_child + S_child
```

### Parent after child close:
```
B0_parent = R_parent_final + S_parent_final
```
where:
```
R_parent_final = R_parent_before_allocation - spawn_cost - child_spent
S_parent_final = S_parent_before_allocation + spawn_cost + child_spent
```

This equation holds for both COMPLETED and ABORTED child closure.

## Finite-Expansion Ranking Theorem

Let cumulative irrecoverable spawn spend over ranked axes be `S_spawn(t)`.

Define:
```
Φ_t = Σ_a w_a * (B0_a - S_spawn(t)_a)
```
over finite granted ranked axes.

**Theorem**: Every admitted expansion has weighted spawn cost at least 1. Spawn cost is transferred to `spent` and never refunded. Therefore:
```
Φ_(t+1) ≤ Φ_t - 1
```
The number of admitted expansions is bounded by `Φ_0`.

**Note**: Conservation alone does not prove termination. The ranking function provides the termination argument through strict descent of irrecoverable spawn spend.

## Pre-Allocation Atomic Rejection Law

These failures leave the parent account snapshot exactly unchanged:
- No proposed expansion
- Semantic-space mismatch
- Invalid cell
- Ranked axes unavailable
- Zero ranked spawn charge
- Over-allocation discovered before `allocate_child`
- Duplicate external envelope identity
- Policy depth exceeded

Full parent snapshot comparison before and after confirms byte-for-byte identity.

## Post-Allocation Compensating Closure Law

After allocation, a child failure is NOT full rollback. It is compensating child closure:

1. Assert child conservation if possible.
2. Seal the child.
3. Close the parent lease with `ABORTED`.
4. Refund only registered child remaining state.
5. Retain child spent.
6. Retain parent spawn cost (irrecoverable).
7. Assert parent conservation.
8. Fold VOID with typed failure evidence.

Post-allocation, parent state differs from pre-allocation state by:
- Spawn spend (irrecoverable)
- Child spend (irrecoverable)
- Consumed/issued authority history
- Closed lease history

## Deterministic Identity Normalization

Normalized authority traces exclude:
- Random nonces
- Random UUIDs
- HMAC signatures
- Wall times
- Monotonic times
- Process-specific identities

First-seen identities are normalized by role:
- `parent-account`
- `parent-predecessor-capability`
- `parent-successor-capability`
- `child-account-0`
- `child-root-capability-0`
- `child-successor-capability-0`
- `child-lease-0`

Raw evidence is retained separately for audit.

## Depth-One Restriction

P0.2 admits only one child depth (`MAX_DEPTH = 1`). The child TRM may propose additional expansion cells, but:
- No grandchild account is allocated.
- No grandchild TRM is invoked.
- Proposal is recorded as `EXPANSION_DEFERRED_DEPTH_LIMIT`.

When the depth axis is granted, child allocation must leave no spendable depth for another child admission under the P0.2 policy. When depth is `NOT_GRANTED` but steps is granted, the policy depth counter still blocks grandchildren at depth one.

## Known Limitations

1. **Conservation does not prove termination** - Only the ranking function proves finite expansion.
2. **Child failure after allocation is not full rollback** - Spawn cost is irrecoverable. Post-allocation state reflects committed spend.
3. **Random capability identifiers are not structural identity** - Secure randomness is preserved for authority safety; normalization enables deterministic comparison.
4. **TRM proposals do not authorize children** - Only the controller's admission decision authorizes allocation.
5. **Halt score does not authorize STOP** - P0.2 does not implement STOP authorization.
6. **No claim of sibling confluence** - P0.2 handles only one child.
7. **No expert loading** - Experts are not activated in P0.2.
8. **No artifact execution** - Decoding is not part of P0.2.
9. **No memory writes** - P0.2 is read-only with respect to memory.
10. **No governance** - Governance is not invoked.
11. **No CUDA requirement** - P0.2 runs offline with deterministic test doubles.
